# UI layer review: Kapelusz / Pass the Hat (`composeApp/.../app/ui/**`, `App.kt`, `Navigation.kt`, `AppDialogs.kt`, `SharedFilesDialog.kt`, `TabLock.kt`)

Read-only review, 2026-10-31. All paths are under `composeApp/src/commonMain/kotlin/com/jacekgajek/kapelusz/app/` unless stated. Line numbers are from the current `local-dev-setup` branch (commit 11db045).

Short verdict first: the code is **well-commented and feature-correct, but every screen is a single composable that does four jobs at once** (fetch + derive data, hold form/dialog state, enforce rules, render). There is no layer between `AppGraph` services and `@Composable` functions, so each screen is wired by hand with 5–13 parameters, keeps 5–22 `mutableStateOf` cells in composition, and re-derives domain data on every recomposition. The owner's complaint ("chaotic, many parameters, many remembers") is accurate and is a *structural* problem, not a tidiness one. The good news: the domain is already pure and shared, `Actions`, `Can`, `Settings`/`settingsFor`, `HistoryController` and `ShareEditorState` are the seeds of the right design, and the migration can be done screen by screen.

### 1.3 How a screen gets its data

- Every band screen receives `state: BandState.Ready` (`data/BandRepository.kt:69`: `band`, `userId`, computed `me`) and reads `band` directly. No screen subscribes to a flow itself; `App.kt:66-68` collects `settings`, `bandState`, `session` and `Navigation.kt:99` passes the `Ready` state down, so *every* recomposition of `Navigation` recomposes every screen argument.
- Services are drilled from `AppGraph` one by one: `Navigation.kt:159` passes `graph.changes, graph.api, graph.settings`; `:178-192` passes seven. `HistorySection(context, api, bands, sync)` (`EventScreen.kt:313`, `HistorySection.kt:39`) exists only because `EventContext` does not carry the services.
- Derived data is computed **inside the composable body** and sometimes memoized, sometimes not:
  - memoized: `EventsScreen.kt:161` (`summaries`), `:190-194`; `BandFundScreen.kt:199-205` (`rows`); `MyCostsScreen.kt:133` (`CostStatuses`); `SummaryScreen.kt:139`.
  - not memoized: `SettleScreen.kt:86-111` settles **every active event** and filters suggestions with `Permissions` on each recomposition; `EventScreen.kt:176` settles the event on each recomposition; `RosterScreen.kt:196-203` sorts/partitions; `CostScreen.kt:161-163,194-197` filters members and events through `Permissions.isAllowed` per item; `ParticipantsSection.kt:107-133`; `TransfersSection.kt:129,264-284` (`handOverSenders` evaluates `Can` per party per recipient).
- Async data (server) is loaded with ad-hoc `LaunchedEffect` + local flags: invites (`RosterScreen.kt:183-193`), history (`HistoryScreen.kt:112-143`), summary (`SummaryScreen.kt:133-138`), event search (`EventsScreen.kt:166-181`), calendar (`CalendarSettings.kt:60-72`), places (`EventFields.kt:209-217`), attachment bytes (`AttachmentViewer.kt:83-97`). Each defines its own `working/failed/busy` trio.

### 1.4 How a screen dispatches changes

- `Actions` (`ui/components/Common.kt:116-169`) wraps `Changes.dispatch` and shows a rejection in the screen's snackbar; `rememberActions(changes, snackbar, undos)` (`:196-203`) is called in 8 screens. Sections get it through `EventContext.actions`. This is the right idea.
- But it is bypassed: `settings/SettingsWiring.kt:61-63` calls `changes.dispatch(op)` directly and discards the `Rejection` ("a refusal can't happen here"); `AttachmentsSection.kt:132,232,241` uses `actions.show(fileStore.attach(...))` (a second path: `Attachments` dispatches internally via `changes::dispatch` injected in `AppGraph.kt:62`).
- Operation construction is inline in click handlers everywhere (e.g. `CostScreen.kt:170-186`, `BandFundScreen.kt:445-464`, `CollectedSection.kt:252-266`, `EventDialogs.kt:102-111`). The "send only what changed" diff logic (`Change(x).takeIf { x != opened.x }`) is written by hand 4 times (`CostScreen.kt:178-185`, `BandFundScreen.kt:455-461`, `CollectedSection.kt:258-264`, `EventDialogs.kt:102-107`).

### 1.6 How navigation is wired

- Routes are typed and serializable (`ui/Routes.kt:9-25`), good.
- `Navigation.kt:157-237` is one `NavHost` with every screen's arguments written inline. Cross-screen results use three different mechanisms:
  1. `savedStateHandle` with string keys: `SHOW_EVERYONE` (`:162-163`, written from `CostScreen` via `onAddedForOther` `:205-207`), `ADDED_COST` (`:169-175`, written at `:208-211`, consumed by `BandFundScreen.addedCost/onAddedCostSeen`).
  2. `Incoming` (`data/Incoming.kt:12-46`): six `MutableStateFlow`s and a plain `var navigatedForBand`, written from `App.kt`, `Navigation.kt`, `SharedFilesDialog.kt:357-385`, `CostScreen.kt:153`, read in `EventScreen.kt:201-244` and `CollectedSection.kt:175-184`. `pendingEventSection` is `Pair<String, String>` whose second half is a **section name as a string** (`"REFUNDS"` `Navigation.kt:203`; `"COLLECTED"`, `"FILES"`, `"REFUNDS"` `SharedFilesDialog.kt:377-382`) matched by `EventSection.entries.firstOrNull { it.name == name }` against a `private enum` in `EventScreen.kt:329`. No compile-time link.
  3. `BandState` transitions + `LaunchedEffect`s (`App.kt:114-124`, `Navigation.kt:106-134,153-155`) that call `navController.resetTo`.
- Role gating is done in the NavHost by composing `BackToEvents` (`Navigation.kt:87-89,166,170,198,229`) and, separately, again inside screens (`EventScreen.kt:173-174` artist can't open others' events; `SettingsScreen.kt:126,131` `LaunchedEffect(Unit) { onBack() }`).
- The `back` lambda (`Navigation.kt:141-145`) and `onOpenPage` (`:219`) each re-implement a "don't double-tap during transition" guard.

### 1.7 Top bar, snackbars, dialogs, undo

- **Top bar**: two components, `TabTopBar` (reads `LocalTopBarState`) and `BackTopBar`. `SummaryScreen.kt:147-157` and `PlayedScreen.kt:99-102` inline a raw `TopAppBar` with a back arrow instead of `BackTopBar`.
- **Snackbars**: a fresh `SnackbarHostState` per screen (`EventsScreen.kt:152`, `CostScreen.kt:128`, `RosterScreen.kt:171`, …). Screens with undo stack two hosts in a `Column` (`CostScreen.kt:210-215`, `RosterScreen.kt:217-222`, `EventScreen.kt:257-262`). Server rejections during sync go to a *different* host in `MainScaffold` (`Navigation.kt:260-265`).
- **Messages inside dialogs** — four mechanisms because a dialog hides the snackbar:
  1. `Actions.dialogs` registry + `DialogNotice` (`Common.kt:126,176-190`) — a mutable list of callbacks registered by `DisposableEffect`, 12 uses.
  2. `AttachmentsSection.inDialog` + its own `notice` timer (`AttachmentsSection.kt:105-115`).
  3. `MemberDialog.message` (`RosterScreen.kt:462,605`), never auto-cleared.
  4. `PaymentRow.copied` (`PaymentDetails.kt:142,148`), `CalendarSettings.copied` (`:63`).
- **Dialogs**: 40 raw `AlertDialog`s + `ConfirmDialog`/`TextInputDialog`. Each is opened by its own `Boolean`/nullable cell in the parent. The "entity vanished while the dialog was open" guard is `LaunchedEffect(Unit) { onDismiss() }` copied 8 times (`CollectedSection.kt:152,169,189,208`, `TransfersSection.kt:298`, `RefundsSection.kt:175`, `ParticipantsSection.kt:359`, `AttachmentViewer.kt:146`).
- **Undo** — three unrelated systems:
  1. Hold-and-withdraw with snackbar: `Actions.runWithUndo` + `UndoStack` + `UndoSnackbars` (`Common.kt:146-160`, `UndoSnackbars.kt`).
  2. Server-history undo: `HistoryUndo.kt` pure functions + `UndoDialog` + `HistoryController.UndoConfirmation`.
  3. Shared-files attach undo via a plain `SnackbarResult.ActionPerformed` (`EventScreen.kt:233-244`).
- **Strings**: `stringResource` is composition-only, so every click handler hoists strings into locals first (`TransfersSection.kt:195-197`, `RosterScreen.kt:518-520`, `AttachmentsSection.kt:121-126`, `JoinDialog` uses `StringResource` ids instead). Placeholders are filled by `.replace("%1$s", …)` in 7 places (`TransfersSection.kt:197,340`, `ArtistSections.kt:159`, `AttachmentsSection.kt:135,146`, `Summaries.kt:81`, `HistoryText.kt:…`). `ParticipantsSection.kt:182-188` even runs an operation from a `LaunchedEffect` just to get its message resolved in composition.

## 2. Specific smells

### 2.1 State held in composition that should be in a holder
Listed in §1.5. Add: `WebInstallHint.kt:43` keeps a **file-level global** `private var dismissedThisVisit by mutableStateOf(...)`; `EventScreen.kt:184` builds `listStates = tabs.associateWith { rememberLazyListState() }` — composable calls inside a collection lambda, whose slot order shifts if `tabs` changes length (artist role change) so the Money tab can inherit the Gig tab's scroll state.

### 2.2 Derived data computed inside composables
`SettleScreen.kt:86-111` is the worst: `active` (settle all events), `mine`, `holding`, `forLeads` all rebuilt per recomposition, and `held()` is re-run per row at `:173`. `EventScreen.kt:176,250,270`. `CostScreen.kt:158-166,194-199`. `TransfersSection.kt:129,264-284`. `ParticipantsSection.kt:107-133,150-151`. `RosterScreen.kt:196-213`. `RefundsSection.kt:78-88`. `LineupPicker.kt:101-116` (groups/visible/toggleable recomputed per keystroke in the search field — acceptable but it is 16 lines of model code in a composable).

### 2.3 Business rules in UI files
- `SettleScreen.kt:106-110`: "awaiting payment counts once the gig is over" — a domain rule in a screen.
- `SettleScreen.kt:90-104`: which suggestions are "mine", what I "hold" (min of own and pair delta) — domain.
- `SettleScreen.kt:147-149` and `TransfersSection.kt:187-188`: `keepsForFund` computed twice, identically, in two files.
- `TransfersSection.kt:264-284`: `transferParties`, `handOverRecipients`, `handOverable`, `handOverSenders` — pure functions over `Settlement`/`Band`, private in a UI file, untested.
- `RefundsSection.kt:83-88`: which costs a non-lead sees as waiting.
- `RosterScreen.kt:562-570`: pre-checks `Artists.holdsMoney` / `Viewers.mayBecome` before an API call, with hard-coded strings that duplicate `RejectionReason` texts.
- `EventsScreen.kt:278-288`, `MyCostsScreen.kt:128-135`, `CostScreen.kt:194-199`, `Navigation.kt:197` (artist may open only own cost).
- `EventDialogs.kt:102-111`: decides to split one Save into `UpdateEvent` + `SetEventAgenda`.
- `HistoryUndo.kt` (pure undo/redo target logic) lives in `ui/screens`; `ShareTargets`, `PeriodSummary`, `Summaries.unsettledEvent/upcomingEvent/myNumber`, `EventSearch` live in `ui/model` though they are app-domain queries with no Compose dependency.

### 2.4 Parameter drilling
`EventScreen` → `HistorySection(context, api, bands, sync)`; `RosterScreen` → `MemberDialog(api, band, member, myUserId, me, …, can, actions, …)`; `BandFundScreen` → `FundEntryDialog(band, initial, me, refundsCosts, refund, onAddCost, onSave, onDelete, onDismiss, actions)`; `CostScreen` → `AttachmentsSection(fileStore, owner, attachments, drafts, onDrafts, editable, removable, actions, undoRemoval)`; `currency` is passed into 20+ leaf composables (`MoneyText`, `shareText`, `PersonRow`, `MemberRow`, `AmountRow`, …) although it is a property of the open band.

### 2.5 Inconsistent naming
- The same thing: `preferences: SettingsRepository` (`EventScreen`, `BandFundScreen`, `SummaryScreen`, `PlayedScreen`) vs `preferences` + `settings: AppSettings` (`EventsScreen`) vs `settings: Settings` (`SettingsScreen`).
- `fileStore: Attachments`, `incoming: Incoming`, `bands: BandRepository`, `changes: Changes` — class names and parameter names disagree.
- Navigation: `onRoster` / `toRoster` / `onOpenMembers` / `onInviteMember` (which also opens the roster); `onBack` / `back`; `onOpenEvent` / `onOpen`.
- Message helpers: `Actions.say`, `Actions.show`, `AttachmentsSection.say`, `notice`, `message`, `DialogNotice`.
- `rememberShareSettlement` / `rememberShareInfo` return lambdas, `rememberPlaceLookup` returns a service, `rememberActions` a dispatcher, `rememberFile` a loaded value.
- `EventContext` vs `state: BandState.Ready` vs `band` — three ways a composable learns what band it is in.
- `*Dialog` names cover `AlertDialog`s, full-screen `Dialog`s (`LineupPicker`, `DetailsEditor` has no suffix), and a bottom sheet (`SharedFilesDialog`).

### 2.6 Where `Can` / permissions are checked — three competing styles
1. `Can` facade (`ui/model/Can.kt`): 13 constructions, sometimes several per screen (`EventsScreen.kt:200,215,283`; `EventScreen.kt:250,270`; `HistoryScreen.kt:162` inside the `LazyColumn` lambda).
2. Raw `Permissions.isAllowed(band, Actor.User(userId), …)` with hand-built probe ops: `CostScreen.kt:157-158,162,204,278-279`; magic `"probe"` literals also in `BandFundScreen.kt:155,296`, `SettingsWiring.kt:67,90` (outside `Can.PROBE`).
3. Raw role tests: `MyCostsScreen.kt:128-131`, `SettleScreen.kt:106`, `EventFields.kt:103`, `SettingsWiring.kt:78,83`, `RefundsSection.kt:83`, `RosterScreen.kt:470,585`; `band.isArtist(userId)` called 13 times although `Can.artist` exists (`Can.kt:47`); `TopBarState.artist` computed separately at `App.kt:188`.

### 2.7 `ui/model` role confusion
`ui/model` mixes: pure formatting (`Formatting.kt`), app-domain queries (`Summaries.kt`, `PeriodSummary.kt` 238 lines, `EventSearch.kt`, `ShareTargets.kt`), a permission facade (`Can.kt`), a text builder that *is* `@Composable` with 72 `Res.string` references (`HistoryText.kt:160-285`), `SettlementText.kt` (pure but takes a `SettlementWords` bag read in `event/ShareSettlement.kt:51-70`), and `Agenda.kt` (half composable). Meanwhile `HistoryLine`/`historyMonth`/`toLines` (`HistoryScreen.kt:79-98`), `HistoryUndo.kt`, `CostStatus.labelRes`/`costStatusText` (`MyCostsScreen.kt:77-94`, used by 3 other files), `settleLabel` (`Common.kt:559`), `Labels.kt` (enum → string maps) and `EventTab` (`data/SettingsRepository.kt:52`, an event-screen page enum) are scattered elsewhere. A reader cannot tell "model" from "domain" from "text".

### 2.8 Files that mix unrelated things
- `ui/components/Common.kt` (563 lines): the dispatcher (`Actions`), a dialog-notice registry, money parsing (`parseMoney`/`withoutGrouping`), 3 dialogs, 2 icon buttons, avatar, status chip, headers, `settleLabel` wording logic, `listWidth`, `VersionLabel`.

- `ui/screens/BandFundScreen.kt` (511): screen + `FundEntryDialog` (143) + `PeopleDialog`.
- `ui/screens/event/EventScreen.kt` (543): `EventContext`, pager/incoming orchestration, `EventSection` enum, `WhenAndWhere`, `Totals`, `FundAmountDialog`, `Problems`, `FilesSection`.
- `ui/screens/MyCostsScreen.kt` hosts cost-status text helpers used by the event screen; `HistoryScreen.kt` hosts `HistoryRow` used by `HistoryController`; `EventsScreen.kt` hosts `AvatarStack`.
- `SharedFilesDialog.kt` sits in the `app` root package next to `App.kt` though it is a screen-level sheet.

### 2.9 Component library consistency
See the table in §1.8: 5 segmented rows, 5 money rows, 4 cost rows, 7 busy buttons, 2 raw top bars, 5 width constants. `IconCircle`/`CostIcon` (`Labels.kt:124-143`) and `Avatar`/`NotInAppIcon`/`GuestIcon` (`Common.kt:245-318`) are good reusable leaves; the `if (guest) GuestIcon() else if (notInApp) NotInAppIcon() else Avatar(...)` choice is nevertheless repeated at `ParticipantsSection.kt:226`, `ArtistSections.kt:85`, `LineupPicker.kt:205`, `SummaryScreen.kt:404`, `RosterScreen.kt:289`.

### 2.10 Strings and resources
832 `stringResource` calls; strings must be resolved in composition, which forces the hoisting/`replace` workarounds above and the `SettlementWords`/`InfoWords` bags (`ShareSettlement.kt:51-70`, `ShareInfo.kt:42,75-83`). `RejectionReason.labelRes()` is resolved for all 43 reasons on every recomposition of every screen that calls `rememberActions` (`Common.kt:200`) and again in `MainScaffold` (`Navigation.kt:261`). `SettingsScreen.kt:187` reads `androidx.compose.ui.text.intl.Locale.current.language` with a fully-qualified name instead of the `language` helper.

### 2.11 Platform `expect`/`actual` leaking into screens
19 UI files call platform functions directly: `rememberCopy`/`rememberShare`/`rememberPaste` (`RosterScreen`, `TransfersSection`, `EventDialogs`, `EventFields`, `PaymentDetails`, `CalendarSettings`, `SecretMenuDialog`, `StuckPushBanner`, `ShareSettlement`, `ShareInfo`), `isAndroidApp()` (`CalendarSettings.kt:83`, `AppBanner.kt:38`), `mapPickerAvailable` (`EventFields.kt:236`, `PlayedScreen.kt:109,179`), `pdfInViewer` (`AttachmentsSection.kt:162,186,218`), `storeListing()` (`SettingsScreen.kt:181`, `UpdateRequiredScreen.kt:38`), `rememberStoreUpdates()`, `appReloader()`. The "copy then say copied/failed" sequence is written 9 times.

### 2.12 Stability
`EventContext` (`EventScreen.kt:136`) is a plain class holding lambdas and is constructed anew at `:270` on every recomposition of `EventScreen`; every section therefore recomposes whenever anything in `EventScreen` changes (e.g. a snackbar). `TopBarState` likewise at `App.kt:175-189`.

### 2.13 Tests
`commonTest/.../ui/` has 13 files / 1 102 lines, all testing **pure functions** (`formatMoney`, `Can`, `undoTargets`, `periodSummary`, `ShareTargets`, `EventSearch`, `UndoStack`, `parseMoney`, `ZoomState`, `inviteCode`). Nothing in a screen body is testable: not "which costs show in My costs", not "is Save enabled", not "what happens on a refused invite". This is the direct cost of the current structure and the main reason to move logic out.

## 3. Target design ("as if built from scratch")

Constraints respected: KMP (Android + Wasm), Compose only, no DI/ViewModel/Decompose/Voyager. Compose runtime `mutableStateOf` is the state primitive; plain Kotlin classes are the holders.

### 3.1 Layers

```
AppGraph (services)            ← unchanged
   │
BandSession                    ← one per open band (new): band flow, me, Can, currency/language, Actions, services
   │
XxxPresenter / XxxForm         ← one per screen or dialog (new): plain class, mutableStateOf inside,
   │                              exposes `state: XxxUiState` (immutable) + intent functions; no Compose UI imports
XxxScreen(session, route, nav) ← thin composable: remember the presenter, map UiState → components, open dialogs
   │
components/*                   ← stateless leaves; no services, no Can, no Band
```

**`BandSession`** (created in `App.kt` when `BandState.Ready`, replaces drilling `graph.*` + `state`):

```kotlin
@Stable
class BandSession(graph: AppGraph, ready: StateFlow<BandState.Ready>, val messages: Messages) {
    val band: Band get() = ready.value.band          // or State<Band> via snapshotFlow bridge
    val userId: String
    val me: Member?
    val can: Can                                     // rebuilt when band changes
    val money: MoneyFormat                           // currency + language, so leaves take Money only
    val actions: Actions                             // dispatch + messages + undo
    val api: ApiClient; val attachments: Attachments; val prefs: SettingsRepository; val incoming: Incoming
    val history: HistoryFactory                      // HistoryController(bandId, …) without 6 ctor args
}
```

**`Messages`** (one per screen scaffold, provided by `LocalMessages`): replaces the per-screen `SnackbarHostState`, `UndoStack`, `Actions.dialogs`, `AttachmentsSection.inDialog`, `MemberDialog.message`, `PaymentRow.copied`.

```kotlin
sealed interface UiMessage {                       // typed, resolved to text only in MessageHost
    data class Rejected(val reason: RejectionReason) : UiMessage
    data class Text(val res: StringResource, val args: List<Any> = emptyList()) : UiMessage
    data class Undoable(val text: Text, val undo: () -> Unit, val gone: () -> Unit) : UiMessage
}
class Messages { fun post(m: UiMessage); val undos: UndoStack; … }
@Composable fun MessageHost(messages: Messages)     // the one snackbar slot; shows undo stack + plain messages
@Composable fun ModalMessages(content: @Composable (inlineNotice: @Composable () -> Unit) -> Unit)
                                                   // inside a dialog: provides a child Messages whose posts render inline
```
`Actions.runWithUndo(op, message: UiMessage.Text)` then takes a resource + args, which kills every `.replace("%1$s")` and the `LaunchedEffect`-to-get-a-string trick (`ParticipantsSection.kt:182-188`).

**Navigation**: keep typed routes. Add:
- `EventSection` moves to `Routes.kt` (public) and `EventRoute(eventId, section: EventSection? = null)`; `Incoming.pendingEventSection` and `SharedFilesDialog.deliver` use the enum.
- Typed results instead of `savedStateHandle` string keys: `CostRoute(costId, forEventId, returnTo: CostReturn = CostReturn.NONE)` where `enum CostReturn { NONE, FUND_REFUND, SHOW_EVERYONE }`; the result is posted through `Incoming.costAdded: MutableStateFlow<CostAdded?>` (typed) or a small `NavResults` object.
- Per-screen navigator interfaces, implemented once in `Navigation.kt` by an `AppNavigator(navController)`:

```kotlin
interface CostNav { fun back(); fun openEvent(id: String, section: EventSection?) }
interface EventNav { fun back(); fun addCost(eventId: String); fun openCost(id: String); fun inviteMember(id: String) }
interface TabNav  { fun settings(); fun roster(); fun openEvent(id: String) }
```

**Permissions**: only `Can`. Every raw `Permissions.isAllowed`, `role == Role.X`, `isArtist`, `"probe"` literal in `ui/` becomes a `Can` method. `Can` moves out of `ui/model` into `app/domain` (it is pure) and gains `editCost(cost)`, `deleteCost(cost)`, `attachTo(owner)`, `addFundEntry()`, `refundFromFund()`, `renameBand()`, `setTreasurer()`, `isLead`, `isViewer`.

**Presentation model**: `ui/model` splits into
- `app/domain/` (pure, tested): `Summaries`, `PeriodSummary`, `EventSearch`, `ShareTargets`, `Can`, `HistoryUndo` functions, the settle-screen queries, `TransfersSection`'s hand-over queries, `costName`/`CostStatus` rules.
- `ui/format/`: `Formatting.kt`, `MoneyFormat`, `SettlementText`, `eventInfoText`.
- `ui/text/`: everything `@Composable` that returns `String` (`describe`, `Labels.kt`, `sharesText`, `displayLabel`).

### 3.2 What a screen file should look like

```
ui/screens/cost/
  CostScreen.kt      ≈ 120 lines: @Composable CostScreen(session, route, nav) { val form = rememberCostForm(...); CostScaffold(form.state, form::save, …) }
  CostForm.kt        ≈ 120 lines: class CostForm(session, route) — state cells, derived UiState, save(), delete(); Saver for rotation
  CostUiState.kt     ≈  30 lines: data class CostUiState(title, payer choices, amount text, errors, canSave, canDelete, refundInfo…)
  (CostFormTest.kt in commonTest)
```

Rules: a `*Screen` composable has ≤ 3 parameters (`session`, route, nav) and no `remember { mutableStateOf }` except for purely visual toggles (menu open, expanded); a `*Form`/`*Presenter` has no `androidx.compose.ui`/`material3` imports; dialogs are one `sealed interface XxxDialog` cell on the presenter; leaves take values and lambdas, never `Band`, `Can`, services or `currency`.

```kotlin
// ui/screens/cost/CostForm.kt  — no Compose UI imports; testable with a Band fixture
@Stable
class CostForm(private val session: BandSession, private val route: CostRoute, initial: CostDraft? = null) {
    private val band get() = session.band
    val existing: Cost? = route.costId?.let(band::cost)
    private val opened: Cost? = existing                              // snapshot for "send only what changed"
    val forEvent: Event? = route.forEventId?.takeIf { existing == null }?.let(band::event)

    var draft by mutableStateOf(initial ?: CostDraft.from(existing, forEvent, session))   // one Saveable data class
        private set
    var dialog by mutableStateOf<CostDialog?>(null); private set     // sealed: ConfirmDelete
    var drafts by mutableStateOf(session.incoming.takeSharedFilesFor(route))   // files shared to a new cost
    private var saved = false

    val state: CostUiState by derivedStateOf {
        val can = session.can
        val editable = existing == null || can.editCost(existing)
        val payers = CostQueries.payers(band, can, forEvent, draft.date)
        val events = CostQueries.eventChoices(band, existing, draft.payerId, draft.eventId, forEvent)
        CostUiState(
            isNew = existing == null, editable = editable, notFound = route.costId != null && existing == null,
            payers = payers, payerLocked = existing != null || payers.size <= 1,
            events = events, eventLocked = forEvent != null,
            amountText = draft.amountText, amountValid = parseMoney(draft.amountText)?.isPositive == true,
            canSave = editable && !saved && parseMoney(draft.amountText)?.isPositive == true && draft.payerId != null,
            canDelete = existing != null && can.deleteCost(existing),
            refundInfo = existing?.let { CostQueries.refundInfo(band, it) },
            attachments = AttachmentsState(owner = existing?.let { AttachmentOwner.OfCost(it.id) }, editable = existing == null || can.attachTo(it), …),
        )
    }

    fun amount(text: String) = edit { copy(amountText = text) }
    fun payer(id: String)     = edit { copy(payerId = id, eventId = eventId.takeIf { CostQueries.eventAllowed(band, id, it) }) }
    fun date(d: LocalDate)    = edit { copy(date = d) }
    fun event(id: String?)    = edit { copy(eventId = id) }
    fun category(c: CostCategory?) = edit { copy(category = c) }
    fun description(t: String) = edit { copy(description = t) }
    fun askDelete() { dialog = CostDialog.ConfirmDelete }
    fun dismissDialog() { dialog = null }

    /** Returns what the navigator should do; nothing on refusal (the message is already posted). */
    fun save(): CostSaved? {
        if (saved || !state.canSave) return null
        val amount = parseMoney(draft.amountText)!!
        val ok = if (existing == null) {
            val id = newId()
            session.actions.run(AddCost(id, draft.payerId!!, amount, draft.date, draft.eventId, draft.category, draft.description.ifBlank { null }))
                .also { if (it) session.attachments.attachAfterSave(id, drafts) }
                .let { if (it) CostSaved.Added(id, forOther = draft.payerId != session.me?.id) else null }
        } else {
            session.actions.run(UpdateCost.diff(existing.id, opened ?: existing, amount, draft)).let { if (it) CostSaved.Updated else null }
        }
        if (ok != null) saved = true
        return ok
    }

    fun delete(): Boolean = existing != null && session.actions.run(DeleteCost(existing.id))

    private inline fun edit(f: CostDraft.() -> CostDraft) { if (state.editable) draft = draft.f() }
}

@Composable
fun rememberCostForm(session: BandSession, route: CostRoute): CostForm {
    val draft = rememberSaveable(stateSaver = CostDraft.Saver) { mutableStateOf<CostDraft?>(null) }  // survives rotation
    return remember(session, route) { CostForm(session, route, draft.value) }.also { form -> SideEffect { draft.value = form.draft } }
}
```

```kotlin
// ui/screens/cost/CostScreen.kt
@Composable
fun CostScreen(session: BandSession, route: CostRoute, nav: CostNav) {          // 3 params
    val form = rememberCostForm(session, route)
    val s = form.state
    AppScaffold(
        topBar = { BackTopBar(stringResource(if (s.isNew) Res.string.add_cost else Res.string.edit_cost), nav::back) {
            if (s.canDelete) IconButton(form::askDelete) { Icon(Icons.Default.Delete, stringResource(Res.string.delete)) }
            TextButton(enabled = s.canSave, onClick = { form.save()?.let { nav.saved(it) } }) { Text(stringResource(Res.string.save)) }
        } },
    ) {
        if (s.notFound) { EmptyState(Res.string.cost_not_found); return@AppScaffold }
        FormColumn {
            s.refundInfo?.let { RefundInfoCard(it) { nav.openEvent(it, EventSection.REFUNDS) } }
            PayerField(s, form::payer)                       // Dropdown / read-only / "paid by X" in one leaf
            if (!s.editable) ErrorText(Res.string.cost_locked)
            MoneyField(s.amountText, form::amount, stringResource(Res.string.amount), autoFocus = s.isNew)
            DateField(form.draft.date, form::date, stringResource(Res.string.cost_date))
            EventField(s, form::event)
            CategoryChips(form.draft.category, form::category)
            OutlinedTextField(form.draft.description, form::description, label = { Text(stringResource(Res.string.description_optional)) })
            AttachmentsSection(s.attachments, form.drafts, { form.drafts = it })
        }
    }
    when (form.dialog) {
        CostDialog.ConfirmDelete -> ConfirmDialog(Res.string.delete_cost_title, Res.string.delete_cost_confirm, Res.string.delete,
            onConfirm = { if (form.delete()) nav.back() }, onDismiss = form::dismissDialog)

    }
}
```

## 5. Noticed, not fixed

Possible bugs, perf traps and feature gaps seen while reading. One line each; not proposing fixes now.

1. `ui/screens/CostScreen.kt:153` — shared photos for a new cost are consumed inside `remember {}` (a side effect) and are not `rememberSaveable`; an Android rotation of the cost form loses the shared files.
2. `ui/screens/SettleScreen.kt:86-111` — every active event is settled, and `can.settleSuggestion` evaluated per suggestion, on every recomposition (e.g. each snackbar tick); `EventsScreen.kt:161` memoizes the same work, `SettleScreen` does not.
3. `ui/screens/event/EventScreen.kt:176` — the event is settled on every recomposition; `Can` built twice (`:250`, `:270`); `EventContext` rebuilt each time, so all sections recompose with the screen.
4. `ui/screens/event/EventScreen.kt:184` — `tabs.associateWith { rememberLazyListState() }` calls a composable in a loop; when `tabs` shrinks (role becomes Artist while open) the remaining tabs take the wrong remembered scroll states.
5. `ui/screens/event/EventScreen.kt:183` — `rememberPagerState(initialPage = …)` only honours the stored tab on first composition; a later change of `stored` is ignored (fine today because settings load before `App`, but fragile).
6. `ui/screens/event/EventDialogs.kt:102-111` — one Save can emit two operations (`UpdateEvent` + `SetEventAgenda`), so History shows two lines and Undo needs two taps, unlike `ShareDialog` which deliberately uses one op.
7. `ui/screens/settings/SettingsWiring.kt:61-63` — rejections are discarded; e.g. `SetTreasurer` on a member who became an artist meanwhile is a silent no-op and `FundSettings.kt:101-103` then flips the switch back off without a word.
8. `ui/screens/event/HistorySection.kt:42` — `HistoryController` gets `context.me?.userId.orEmpty()` while `HistoryScreen.kt:109` passes `state.userId`; for an unlinked user the pending undo line is attributed to user `""`.
9. `ui/screens/RosterScreen.kt:277` + `Common.kt:433` — `TextInputDialog` always dismisses after `onConfirm`, so a refused `AddMember` closes the dialog and the typed name is lost (other dialogs keep their input on refusal, `ParticipantsSection.kt:346`).
10. `ui/screens/RosterScreen.kt:497` — Rename sends untrimmed `name` while the enabled check compares `name.trim()`; relies on the reducer trimming.
11. `ui/screens/RosterScreen.kt:462,605` — `message` in `MemberDialog` is never cleared until the dialog closes, unlike `DialogNotice` (8 s); two stale messages can stack.
12. `ui/components/Common.kt:200` and `Navigation.kt:261` — 43 `stringResource` lookups for every `RejectionReason` on every recomposition of every screen with `rememberActions`, plus `MainScaffold`.
13. `ui/screens/event/CollectedSection.kt:175-184` and `EventScreen.kt:213-221` — two consumers of `incoming.sharedHandover`; the collected-money dialog only opens once the `COLLECTED` list item is composed, which depends on `pendingEventSection` having scrolled there first. Works, but ordering is implicit.
14. `Navigation.kt:203`, `SharedFilesDialog.kt:377-382` — section names as strings matched against a `private enum` (`EventScreen.kt:329`); a rename compiles and silently stops scrolling.
15. `ui/screens/AttachmentsSection.kt:162` and `:218` — `viewable` computed twice with the same expression; if one is edited the viewer opens on the wrong index.
16. `ui/components/WebInstallHint.kt:43` — process-global mutable state in a component file; survives sign-out/sign-in.
17. `ui/screens/MyCostsScreen.kt:120` + `Navigation.kt:163` — `onOpenCost: (String?) -> Unit` where `null` means "add a cost"; the meaning is only in the FAB call site (`:142`).
18. `ui/screens/BandFundScreen.kt:155,296`, `SettingsWiring.kt:67,90`, `CostScreen.kt:278-279` — magic `"probe"` ids outside `Can.PROBE`; if the server ever validates ids the UI silently hides actions.
19. `ui/screens/event/TransfersSection.kt:187-188` vs `SettleScreen.kt:147-149` — `keepsForFund` duplicated; a change in one (e.g. pairs) will diverge.
20. `ui/screens/HistoryScreen.kt:162` — `Can(...)` constructed inside the `LazyColumn` content lambda on each recomposition.

23. `ui/screens/SummaryScreen.kt:134,139` and `PlayedScreen.kt:84-86` — `today()` is read on every recomposition and used as a `remember`/`LaunchedEffect` key; harmless, but the summary is recomputed at midnight only when something else recomposes.

30. `ui/screens/BandFundScreen.kt:448-450` — on a partial failure among several payers the dialog stays with the remaining payers but `description`/`amount` are unchanged, so a retry can double-post the entries that succeeded if the failure was transient and the user edits the amount first (the comment claims no doubles; that holds only if nothing else is edited).
